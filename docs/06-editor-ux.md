# Anselse · 编辑器交互方向（B3 决策文档）

> 起因：创始人提议采用 Canva 式"按 shot 分 screen"的通用形态。本文档记录评估结论与最终方向，供 B3 低保真验证。

## 结论

**Canva 的 shot-strip 骨架保留；screen 内部不做画布；Remix 槽位视图作为第一入口。** 三层结构：

```
第 1 层 · 槽位视图（Remixer 默认首屏）
  fork 后先看到"可以换的槽位"：主体 / 台词 / 光线 / 时长 / 结尾
  与原作 diff 高亮；改完即可渲；「打开完整分镜」进入第 2 层
        │
第 2 层 · Shot-strip（结构层，≈ Canva screens）
  横向分镜条，一 shot 一卡：编号 · 时长 · 景别 · 运镜摘要 · 对白摘录
  与已验证模板的"镜头 01-04"结构同构；点卡进入第 3 层
        │
第 3 层 · 剧本卡（shot 内部，非画布）
  竖排 beat 卡：状态标题 + 可见动作 + 内联对白块（正是已验证 prompt 的结构）
  底部一条轻量 beat 时间条（拖动调节奏），非 NLE 时间轴
  运镜/景别用受控选择器，只亮 capability 已验证的项
```

## 评估依据

**Canva 形态成立的部分**
- 域模型同构：已验证 30s 模板本身就是"镜头 N"分块 → shot 即 screen，映射零损耗。
- 心智成本低：创作者都用过 Canva/CapCut，分镜条不需要教学。
- fork 落地自然：FTUE = fork → 分镜条即所见。

**必须偏离的两点**
1. **Screen ≠ 画布**。画布隐含"空间自由排版"的承诺，而 shot 内容是时间性/文本性的（beat/对白/运镜），模型不会兑现任意空间构图——交互形态不能开出 capability 层兑现不了的支票。剧本卡形态与 prompt 的真实结构（每句一行/beat 分段/对白块）一一对应，编辑所见即编译所得。
2. **主入口是"改"不是"创"**。产品叙事是 fork：Remixer 的首要动作是换槽位，不是从零编排。槽位视图（带原作 diff）是竞品没有的交互，也是把"80% 用户只改 20% 字段"翻译成界面。Director 才需要完整分镜编辑，走第 2/3 层。

**顺带的 schema 修正**：Shot 升为一等结构（`recipe.shots[].beats[]`），替代拍平的 beats——UX 与数据模型保持同构（记入 05-dev-plan 决策记录）。

## B3 低保真要验证的问题

1. 槽位视图的槽位集合对不对？（主体/台词/光线/时长/结尾——还是应该由 Director 发布时自定义"暴露哪些槽位"？后者更符合"配方作者决定可变部分"，倾向后者，验证之）
2. Remixer 是否会想进第 3 层？（如果 90% 不进，第 3 层可以晚做）
3. beat 时间条要不要 v1 做？（SD 模板不用逐 beat 时间戳，Kling 分段才需要——可能 v1 省略）
4. shot-strip 上"每卡显示什么摘要"最能帮助扫读？

## 定稿的交互原则

- 界面语言用创作者词汇（镜头/表演/fork/重拍），internal 术语（schema/patch/adapter）永不出现。
- 每个可交互控件必须对应 capability 已验证的控制轴；未验证的置灰并给一句原因。
- 编辑所见（剧本卡结构）≈ 编译所得（prompt 结构），不造第二套心智模型。
