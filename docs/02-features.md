# Anselse · Feature 方案

> 原则：每个 feature 必须服务三个复利回路（切换成本 / 分发 / 数据）之一，否则砍。

---

## 0. 产品原子：Direction Recipe

一切 feature 围绕一个原子单元展开。**Recipe = 一个镜头的结构化导演意图**，model-neutral、可版本化、可 fork、可层叠 patch。

```
Recipe
├─ 场景层      主体（引用角色锚点）· 环境 · 光线 · 风格参照
├─ 表演层      beat 时序（t → 动作/情绪/微表情/台词）· 情绪递进曲线
├─ 摄影层      景别 · 机位 · 运动路径（受限词汇表）· 构图
├─ 约束层      时长 · 画幅 · 参考帧（首/尾帧）
└─ 绑定层      目标 adapter + 每 adapter 的覆盖项（可选）
```

> **词汇表与 schema 由产品自有、由交付性数据裁决**：只收录经红线测试（E3）验证"模型真能兑现"的条目，宁少而准；未验证条目在 UI 中显式标注。内部方法论（团队的导演 skill：行动逻辑链、Beat Graph、Camera Unit、逐模型规则）是候选条目的**主要来源之一**，但收录以测试结论为准，不与任何单一方法论绑定——面向用户的字段用创作者的语言（如"情绪递进"），不暴露内部理论术语（如 `display_policy`）。深层戏剧学字段属于"高级/助手代填"层，不是每个用户的必填项。

## 1. Feature 地图（按模块）

### A. Recipe 编辑器（导演工作台）—— 核心工具

| Feature | 说明 | 服务的回路 |
|---|---|---|
| **A1 结构化调度面板** | 按场景/表演/摄影/约束四层填写；beat 时序用轻量时间轴（拖动 beat 点、每点挂动作/情绪/台词） | 切换成本 |
| **A2 Capability 感知 UI** ⭐ | 选定目标模型后，**只亮该 adapter 声明"能兑现"的控制轴**；不可兑现的轴置灰并说明。这是"交付性"风险的产品化解法 | 数据 |
| **A3 编译预览** | 一键查看 Recipe 被 `resolve()` 编译成的目标模型原生 prompt/控制信号（可读、可微调编译结果但不鼓励）——让高手信任系统，也是教学工具 | 切换成本 |
| **A4 词汇表助手** | 表演/运镜字段提供受控词汇的联想与解释（"渐进式崩溃"是什么、哪个模型兑现得好），背后是研究知识库 | 数据 |
| **A5 连续性锚点（字段级）** | 角色/风格/场景可保存为项目内资产（参考图+描述），Recipe 引用之；v1 只做"引用注入"，不承诺跨镜一致性 | 切换成本 |

### B. Take 系统（渲染与迭代）

| Feature | 说明 | 服务的回路 |
|---|---|---|
| **B1 渲染队列** | Recipe 版本 → adapter → 异步渲染 → Take；排队/进度/失败重试 | — |
| **B2 Take 对比** | 同一 Recipe 版本的多次渲染并排对比（A/B/C），标记 selected/discarded | 数据 |
| **B3 Take↔Recipe 强绑定** ⭐ | 每个 Take 永久记录：产生它的 Recipe 版本 + adapter + 编译后的完整 spec。**任何视频都能回放出它的配方**——demo+recipe 发布的技术保证 | 切换成本 |
| **B4 兑现度反馈** | 用户对 Take 打标："镜头运动做到了吗/表演到位吗"（每轴一个 👍/👎）——直接喂交付性数据集 | 数据 ⭐ |
| **B5 变体渲染** | 改一个轴 → 渲染，自动成为 Recipe 的一个 patch 版本，谱系保留 | 切换成本 |

### C. 社区（配方库与 remix）

| Feature | 说明 | 服务的回路 |
|---|---|---|
| **C1 发布 = Demo + Recipe** ⭐ | 发布单元强制为「选定的 Take + 其 Recipe」，二者不可拆分。无"仅发视频"选项 | 分发 |
| **C2 一键 Fork** | fork = 复制 Recipe 引用 + 建立谱系边；进入编辑器即可改主体/台词/风格重渲 | 分发 + 切换成本 |
| **C3 Remix 谱系** | 每个作品展示"源自谁、被谁 remix、改了哪些轴"（diff 可视化）；原作者在下游作品上永久署名 | 分发 |
| **C4 配方浏览** | 按景别/情绪/运镜/模型/兑现率筛选；"这个模型上表现最好的配方"榜单 | 数据 |
| **C5 收藏与合集** | 个人配方库、收藏夹、（后期）付费配方 | 切换成本 |

### D. FTUE（首次体验流）

```
落地页：精选 demo 视频墙（每个卡片 = 视频 + "查看配方"按钮）
  → 点开任一 demo：左侧视频循环播放，右侧 Recipe 四层结构展开可读
  → 「Fork 这个镜头」→（注册）→ 编辑器打开，预填该 Recipe
  → 引导改一个轴（如换主体描述/换一句台词）→ 渲染第一个 Take
  → 对比自己的 Take 与原 demo → 发布或继续改
```

设计要点：**新用户的第一次生成永远从一个已被验证可兑现的配方出发**——首次体验的成功率被结构性拉高，这同时是最强的教学（看得见"好的调度长什么样"）。

### E. Adapter 与平台管理

| Feature | 说明 |
|---|---|
| **E1 Adapter 注册表** | v1 内置 2-3 个：Kling 3.0、Seedance 2.0（研究已覆盖），可选 +1 国际模型（Veo/Runway API 视可用性）|
| **E2 Capability 声明** | 每个 adapter 静态声明控制轴支持度（supported / partial / none）+ 兑现率数据动态修正 |
| **E3 交付性红线测试（内部）** ⭐ | 一套标准探针 Recipe（每轴数条），新模型/新版本接入时批量渲染 + 人工评分 → 生成该 adapter 的 capability 声明与词汇表白名单。**上线前先跑，决定 v1 敢承诺什么** |
| **E4 密钥与计费** | 平台代付渲染（用户买额度）为主；Pro 用户可绑自有 API key |

## 2. 优先级（无排期，仅依赖序）

```
P0（缺一不可的最小闭环）
  E3 红线测试 → 框定词汇表
  Recipe schema + A1 编辑器 + A2 capability UI
  E1/E2 两个 adapter（Kling + Seedance）
  B1 渲染 + B3 Take↔Recipe 绑定
  D FTUE（用创始团队自产的 50-100 个 Recipe 冷启动）

P1（闭环跑通后）
  C1-C3 社区发布/fork/谱系
  B2/B4/B5 take 对比、兑现度反馈、变体
  A3/A4 编译预览、词汇表助手

P2
  C4/C5 浏览/榜单/收藏、A5 锚点资产化、E4 自带 key、付费配方
```

> 注意 P0 的第一项是**测试而非功能**：先知道模型今天能听懂多少，再决定 Recipe 抽象做多细。顺序不可颠倒。
